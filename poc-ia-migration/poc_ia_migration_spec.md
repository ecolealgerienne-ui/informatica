# POC — AI-Powered ETL Migration Agent
## Specification Document for Claude Code
*Version 1.0 — June 2026*

## 1. Context & Objective

### What this POC proves
This POC demonstrates the **technical feasibility** of using specialised AI agents to automatically convert Informatica PowerCenter XML workflows into Python ETL code, replacing the manual conversion work currently done by migration engineers.

This is **NOT** a production system. It is a controlled experiment to validate:
1. Can a Parser Agent extract a clean, structured canonical JSON from a real PowerCenter XML?
2. Can a CodeGen Agent generate functional Python ETL code constrained by internal standards?
3. Can a Fixer Agent detect and correct errors in generated code?
4. Can a QA Agent produce a usable Data Diff comparison report?

### Target stack for this POC
- **Input:** Informatica PowerCenter XML export (one workflow)
- **Output:** Python standalone ETL code (pandas/Polars)
- **LLM:** Claude Sonnet 4.6 via Anthropic API (already configured)
- **Runtime:** Python 3.11+ local environment
- **No PySpark for this POC** — Python standalone only, simpler to run and validate locally

## 3. Sample PowerCenter XML — What to Generate

Run `setup/generate_sample_xml.py` first to create the input file.

### Workflow description: `wf_clients_dim`
This is a **deliberately realistic** PowerCenter workflow that includes the transformation types most commonly found in real estates. It is intentionally at **medium complexity** — enough to be meaningful, not so complex it blocks the POC.

**Transformations included:**

| # | Transformation | Type | Purpose |
|---|---|---|---|
| 1 | `SQ_CLIENTS` | Source Qualifier | Reads from Oracle `CLIENTS` table with SQL Override (date filter) |
| 2 | `LKP_STATUT` | Lookup (Connected, static) | Enriches with `REF_STATUT` table to get label |
| 3 | `EXP_TRANSFORM` | Expression | Cleans strings (LTRIM/RTRIM/UPPER), calculates age, formats dates |
| 4 | `FIL_ACTIVE` | Filter | Keeps only active clients (STATUT_CODE != 'I') |
| 5 | `TGT_DIM_CLIENTS` | Target | Writes to `DIM_CLIENTS` table |

**Session variables / Parameter File:** one variable `$$BATCH_DATE` passed via parameter

**Source:** Oracle table `CLIENTS` (10 columns)
**Target:** Oracle table `DIM_CLIENTS` (12 columns including audit fields)

## 4. Agent Specifications

### Agent 1 — Parser Agent (`agents/parser_agent.py`)

**Input:** PowerCenter XML file path
**Output:** `output/01_canonical_json/wf_clients_dim.json`

**What it does:**
- Parses the XML using Python's `xml.etree.ElementTree`
- Extracts: mapping name, source tables, target tables, all transformations with their type/expressions/ports, connectors (data flow graph), session variables, parameter files
- Flags complexity: `LOW` / `MEDIUM` / `HIGH` / `CRITICAL` per transformation
- Detects: SQL Overrides, Lookup types (Connected/Unconnected/Dynamic), Java Transformations, proprietary functions
- Determines routing: `PYTHON` / `CLOUDERA` / `DATABRICKS`
- Produces a **canonical JSON pivot** — the single source of truth for all downstream agents

### Agent 2 — CodeGen Agent (`agents/codegen_agent.py`)

**Input:** Canonical JSON from Agent 1

**What it does:**
- Reads the canonical JSON
- Loads `rag_base/python_templates.md` and `rag_base/transformation_map.json`
- Calls Anthropic API with a carefully constructed prompt

### Agent 3 — Fixer Agent (`agents/fixer_agent.py`)

**Input:** Generated Python code from Agent 2
**Output:** `output/03_fixed_code/wf_clients_dim_fixed.py` + `output/03_fixed_code/fix_report.json`

**What it does:**
- Runs **static checks** (no LLM needed) first:
  - `ast.parse()` — syntax validation
  - Import check — all imports resolvable
  - Function signature check — mandatory functions present (extract, transform, load, main)
  - RAG Base compliance — no functions used that are not in transformation_map.json
- If static checks pass → calls Anthropic API for **semantic review**:
  - Are the Informatica expressions correctly translated? (DATEDIFF, TO_DATE, LTRIM/RTRIM)
  - Is the Lookup implemented as a merge/join, not a loop?
  - Is the Filter condition correctly negated?
  - Is the load function idempotent?
- Auto-corrects what it can, flags what it cannot
- Maximum **3 correction cycles** before human escalation
- Produces a structured fix report

## 5. RAG Base Content

### `rag_base/transformation_map.json`
Mapping table: Informatica function → Python equivalent

```json

  "LTRIM": "str.lstrip()",
  "RTRIM": "str.rstrip()",
  "UPPER": "str.upper()",
  "LOWER": "str.lower()",

  "SYSTIMESTAMP": "datetime.now()",
  "TO_DATE": "pd.to_datetime()",

  "IIF(cond, true_val, false_val)": "numpy.where(cond, true_val, false_val)",

  "NVL(col, default)": "col.fillna(default)",

  "ROWNUM": "df.head(n) or df.iloc[:n]",
  "CONNECTED_LOOKUP": "df.merge(ref_df, left_on=condition_col, right_on=ref_key, how='left')",
  "FILTER": "df[condition]"
}
```

### `rag_base/python_templates.md`
Mandatory patterns for generated code:
- Batch structure (extract / transform / load / run_batch)
- Idempotence pattern (staging table + atomic swap)
- Audit logging format
- Lookup as merge (never as a Python loop)
- All datetime operations using pandas vectorised operations (no `.apply()` loops)

## 6. Data Diff Tolerance Matrix

| Column | Tolerance | Justification |
|---|---|---|
| CLIENT_ID | Zero gap | Key column |
| NOM_CLEAN | Exact string match after normalisation | String cleaning deterministic |
| PRENOM_CLEAN | Exact string match after normalisation | String cleaning deterministic |
| AGE | ± 1 year | Edge case on birthday date vs SYSDATE timing |
| STATUT_CODE | Zero gap | Categorical — no tolerance |
| STATUT_LIBELLE | Exact match | Lookup from reference table |
| EMAIL_LOWER | Exact match | String operation deterministic |
| SEGMENT_CODE | Zero gap | Passthrough — no transformation |
| PAYS_CODE | Zero gap | Passthrough — no transformation |
| DATE_CREATION | Zero gap | Passthrough |
| BATCH_DATE | Exact match | Controlled by parameter |
| DW_LOAD_DATE | **Exclude from comparison** | Changes by definition (current timestamp) |

### Pipeline orchestrator (`pipeline/run_pipeline.py`)
```python
"""
Main pipeline: runs all 4 agents in sequence.
Stops and escalates if any agent returns a FAILED or ESCALATE status.
"""
import json, logging
from agents.parser_agent  import ParserAgent
from agents.codegen_agent import CodeGenAgent
from agents.fixer_agent   import FixerAgent
from agents.qa_agent      import QAAgent

logging.basicConfig(level=logging.INFO,
    format='[%(asctime)s] [%(name)s] %(levelname)s — %(message)s')

def run():
    # Step 1 — Parse
    parser  = ParserAgent("input/wf_clients_dim.xml")
    json_output = parser.run()
    print(f"✅ Parser Agent — routing: {json_output['routing_decision']['target_platform']}")

    # Step 2 — CodeGen
    codegen = CodeGenAgent(json_output)
    code_output = codegen.run()
    print(f"✅ CodeGen Agent — {len(code_output.splitlines())} lines generated")

    # Step 3 — Fix
    fixer   = FixerAgent(code_output, json_output)
    fix_result = fixer.run()
    print(f"✅ Fixer Agent — {fix_result['cycles_used']} cycles, status: {fix_result['status']}")
    if fix_result['status'] == 'ESCALATE':
        print("🚨 Human intervention required — see fix_report.json")
        return

    # Step 4 — QA
    qa      = QAAgent(fix_result['output_file'], "tests/expected_output.csv")
    qa_result = qa.run()
    print(f"✅ QA Agent — {qa_result['anomalies_count']} anomalies detected")
    print(f"📄 Report: output/04_data_diff_report/data_diff_report.html")

if __name__ == "__main__":
    run()
```
